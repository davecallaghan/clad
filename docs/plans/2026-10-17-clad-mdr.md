# clad-mdr Implementation Plan (monitoring, detection and response)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add MDR to clad. clad-gateway records input signals. A new `clad-mdr` worker reconciles the infra log, GIL, chain and degraded records on an interval. It writes heartbeats and alerts with severity, taxonomy and due time, posts them to a webhook, and opens incidents with an evidence locker for P1 and P2. personal_finance then runs it in the pod and takes the final measurement with probes.

**Architecture:**
- New sbt module `mdr` (package `clad.mdr`), depending on `gateway` and `monitoring`.
- Each cycle reads the stores through a read-only source and turns rows into clad `GovernanceEvent`s.
- The events feed clad's `MonitoringEngine`. The detectors implement clad's `EventDetector`/`WindowDetector` traits; clad's `ComponentHealthDetector` is reused.
- An `AlertSink` writes `mdr.alert`, posts the webhook and opens incidents.
- The worker's state lives only in the stores: the last heartbeat is the cursor, and alert dedupe keys prevent repeats. A restart therefore neither repeats nor loses alerts.

**Tech Stack:** as the gateway plan (Scala 3.3.8, sbt, upickle, SnakeYAML, PostgreSQL JDBC, scalatest); the JDK `HttpClient` for the webhook. No new libraries.

**Spec:**
- personal_finance `docs/superpowers/specs/2026-10-15-clad-enforcement-design.md`, section 9 (input detectors, the MDR detector table, severities, containment) and section 10 (the final measurement with probes).
- clad `docs/specs/2026-10-16-clad-gateway-design.md`, sections 4 (the `mdr` module), 8 (the `mdr` schema), 10 (the MDR worker) and 14.2 (JVM footprint).
- conformance's `MdrChecks` (R-MDR-ALERT, R-MDR-LIVE) and `GhostProbe` (R-PROBE-GHOST) define what the bundle must show.

**Depends on:** the ROC plan (`docs/plans/2026-10-17-clad-gateway-roc.md`). The `flags` detector reads ROC `flag` outcomes, and the final measurement expects ROC records.

## Review Focus

- **Ghost alerts must match conformance's own reconciliation.** Every interaction id conformance counts as a ghost (`LinkageChecks.ghostIds`) must appear in some alert's `interaction_ids`. Every infra entry without an id must be covered by an alert from detector `ghosts` raised at or after the entry and within `detectionDelaySeconds`. The round-trip test (Task 7) asserts R-MDR-ALERT SATISFIED on a bundle containing both kinds.
- **Not every slow interaction is a ghost.** A GIL entry younger than `in_flight_grace_seconds` with no records yet is in flight, not a ghost. Once the grace period passes, it is alerted exactly once, even if MDR restarts in between.
- **Heartbeats per detector, every cycle, even when a detector fails.** A failing detector writes its heartbeat and an alert about itself, P2 governance `detector_failed`. A detector that stops reporting shows up as a gap in R-MDR-LIVE, never as silence that reads as health.
- **Incident lockers are immutable and complete.** The locker is a bundle export of the alert window, and conformance can read it. Its files are made read-only. A failed export is itself an alert, and the incident row records the failure.
- **Webhook failure loses nothing.** The alert row is written before the webhook POST. A failed POST is logged with the alert id and retried on the next cycle until it succeeds. The `mdr.alert_delivery` table records each delivered alert.

Rules:
- **The read window.**
  - On the first run (no heartbeat), the window starts at the earliest infra or GIL timestamp. Ungoverned calls made before MDR existed are therefore alerted, which is the true state.
  - Afterwards it starts at the last heartbeat minus `in_flight_grace_seconds`, so interactions that were in flight at the last cycle are re-examined.
  - `lookback` widens it for the block-rate baseline.
- **Infra entries** come from the egress log through the gateway's `CaddyLog` reader, the same reader the export uses, so MDR and the bundle see one infra log.
- **Events:**
  - degraded records → `ComponentFailure`, with posture from the record;
  - ROC records with outcome `block` or `fallback:*` → `OutputBlocked`;
  - every record → `EvaluationCompleted`;
  - each input signal → a `ViolationDetected` with property `input:<category>`, consumed only by the input detector;
  - the rest of the reconciliation (ghosts, in flight) happens in the detectors from the snapshot, because events alone cannot express "absent".

**Files:**

**Interfaces:**
- Produces:

```scala
final class Cycle(source: Source, detectors: Vector[Detector], writer: AlertWriter, heartbeat: (String, java.time.Instant) => Either[String, Unit],
                  cfg: MdrConfig, clock: () => java.time.Instant):
  def once(): Either[String, CycleReport]   // CycleReport(window, alertsWritten, detectorFailures)
```

`clad-mdr` commands:
- `run`: loop `once()` every `interval_seconds`. A failed cycle is logged and the next one runs; never exit on a cycle failure.
- `once`: a single cycle, for tests and the measure script.
- `check`: config, DB and egress log readable; exit 0 or 1.

Per cycle:
1. Compute the window and take the snapshot.
2. Run every detector.
3. Write each detector's heartbeat with the cycle time, whether it succeeded or failed.
4. A failing detector writes an alert: P2 Governance, detector `<id>`, key `detector_failed:<id>:<cycle time>`.
5. Write the alerts.
6. Call `redeliver` for undelivered alerts.

A snapshot failure writes no heartbeat. That is the honest state: the window was not monitored, and R-MDR-LIVE shows it.
